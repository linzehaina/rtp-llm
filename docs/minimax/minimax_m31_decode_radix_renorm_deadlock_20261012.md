# Decode precision campaign: Radix TopK renorm deadlock

## Verified failure and scope

The 32-client PD4+4 accuracy campaign stopped making progress after 5409
successful samples. CUDA 13.2 cuda-gdb identified the live kernel as
`flashinfer::sampling::RadixTopKRenormProbKernel_MultiCTA<1024,4,false,float,int>`:
60 blocks, 1024 threads per block, and a remaining nonleader CTA (block 23).
The native engine waited for an event in `consumePendingAcceptLenMetrics`;
bookkeeping also waited for a transfer event. These CPU waits are consequences
of unfinished GPU work. The evidence does not establish interference by another
service or a cudaGraphLaunch bottleneck.

The older CUDA 13.0 debugger did not expose live kernels and is not evidence of
an idle GPU. The CUDA 13.2 dump identifies the stalled kernel; the attempted
instruction disassembly does not establish the exact program counter.

Evidence directory:
`/data0/ruixuan.zrx/minimax-m31-dev/1012_decode_latest_candidate_full_quality`

- `decode_rank2_gpu_wait_kernels_cuda132.txt`: live kernel and CTA.
- `decode_rank2_wait_detail.txt`: native event-wait stack.
- `precision_stall_evidence.json`: campaign failure evidence.

## Synchronization mechanism and narrow correction

`AdvanceRadixGroupBarrier` publishes each CTA's arrival and waits for the
monotonic counter to reach the current phase's target. At kernel exit the leader
reset the counter to zero. The leader passing the barrier does not imply that
every other CTA has already observed the target. A delayed observer can see the
reset value and wait forever, because no CTA will publish another arrival.

Only the terminal histogram/counter reset of `RadixTopKRenormProbKernel_MultiCTA`
was removed. Pivot selection, retained ties, output normalization, and other
Radix kernels were not changed. The RTP caller in `sampling/api.cu` allocates a
private, freshly zeroed 1 MiB state buffer per invocation. It does not need the
terminal cleanup for reuse. Any future buffer reuse must initialize the buffer
after all preceding CTAs have completed and preserve the required stream order.

   arrival, before observing the final counter. The original kernel times out

   retains all ties, and normalizes the retained probabilities. Finite values,
   numerical agreement, and exact support are checked. See
   `radix_large_vocab_regression.{json,log}`.
3. The independent installation `native_radix_fix_install` has identical
   Python bytes to the previous candidate. Among six native libraries only
   `librtp_compute_ops.so` changed. See `radix_fix_runtime_identity.json`.

## E2E quality and remaining performance validation

The existing 5681-sample generation campaign completed. The user subsequently
narrowed the primary LongBench deliverable to the historical 160 samples over
8 tasks (20 per task). Re-scoring these saved responses with the same official
metrics gives baseline 66.8703545 and candidate 66.7683125. No new baseline was
generated. There are 5409 preserved successful responses and 272 responses
generated by the repaired runtime. Twenty-seven
transport timeout records remain archived and are excluded by transport status,
not by answer correctness. All completed wrong answers are retained.

The resume checkpoint records both launch identities and the arithmetic-
preserving fix. The final score combines responses from two native binaries;
it must not be described as 5681 new responses from the repaired binary. Native
MAL covers only the new generation window. See
`quality_candidate/resume_radix_checkpoint/{resume_filter_receipt,runtime_compatibility}.json`.

Primary dataset scoring, strict native MAL, sampled16, and lifecycle gates passed
their execution/integrity checks. Aggregate candidate scores: Math500 418/500,
GSM8K 1137/1319, HumanEval 143/164, and AIME24 completed final answers 26/30.
Score differences are for user review, not a claim of zero quality regression.
Native MAL is 2.80470635 for the 272-request repair window only. See
`dataset_score_handoff.json` and `quality_radix_state.json` in the campaign folder.
One fresh independent final review found no confirmed executable production
blocker; its documentation finding is corrected here. Final repaired-runtime
performance repeatability and the latest timeline are still being collected
under `1012_decode_radix_final_performance`. Sample/propose CPU bubbles remain the next round's
optimization work; this correctness fix does not claim to remove those bubbles.
